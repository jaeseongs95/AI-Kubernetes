## 판정

앞선 정상 경로 검증은 동시 게시 경쟁과 잘못된 DB의 거짓 통과를 충분히 다루지 못했다. 이번 감사는 원격 기준선을 보존한 뒤 세 독립 검토 경로와 통합 검토를 통해 **도구·데이터 결함 6건, 착수 정책 불일치 1건, 제품 설계 보강 3건**을 확인했다. 재현한 도구 결함은 수정하고 회귀 검증을 추가했다. 제품 계획은 20개 태스크의 기준을 보강했다.

**장부 도구 회귀 53개가 통과했다.** SQLite와 생성 SQL/Markdown의 일치, SQL 복원 후 전체 스키마·행·버전의 동등성, 첫 출시 의존 관계를 확인했다. 제품 계획의 세 지적 사항은 별도 검토자가 수정 DB를 다시 읽고 반례를 대조했다.

이 결과는 **개발 장부 도구와 계획의 검증**이다. 실제 Windows 제품·로그인·모델 실행·AGS/VM gate·원격 클러스터 구현은 아직 검증하지 않았다. 82개 제품 태스크는 모두 `todo`, 제품 완료 evidence는 0개다. 이번 감사 자체를 제품의 AIK-061 완료로 기록하지 않았다.

### 1. 동시 게시 경쟁은 실제 명령 두 개로 재현했다

수정 전에는 A가 AIK-001 상태를 DB에 커밋한 뒤 파일 교체 직전에 멈추고, B가 AIK-002를 변경해 모든 파일을 게시한 뒤, A가 오래된 파일을 게시할 수 있었다. 두 명령은 모두 성공했다.

| 최종 데이터 | AIK-001 | AIK-002 |
| --- | --- | --- |
| 수정 전 SQLite | in_progress | in_progress |
| 수정 전 SQL·Markdown | in_progress | **todo** |
| 수정 후 SQLite·SQL·Markdown | in_progress | in_progress |

수정본은 같은 실제 DB 경로에 대해 `status`, `export`, `report`를 직렬화한다. POSIX `flock`과 Windows `msvcrt.locking` 분기를 제공하며 잠금 대기는 최대 10초다. symlink는 실제 경로를 공유하고 hardlink DB 별칭은 명시적으로 거절한다. 잠금 파일은 삭제하지 않고 유지해 잠금 대상 파일이 갈리는 상황을 피한다.

파일 여러 개를 하나의 원자적 트랜잭션으로 만든 것은 아니다. DB 커밋 전 생성 실패는 롤백한다. 커밋 뒤 파일 교체 실패는 커밋 사실과 `export`/`report` 복구 명령을 알린다. 외부 직접 SQLite 편집은 이 도구의 잠금에 참여하지 않으므로 별도 편집과 유지보수 명령을 동시에 수행하지 않는 운영 조건을 명시했다.

### 2. DB가 열리는 것과 장부가 유효한 것은 별도로 검사한다

수정 전 정상 SQL 뒤에 아래 구문을 추가하면 잘못된 상태가 복원되고 후속 `validate`도 성공했다. 이후 `report`는 상태 이름 조회 중 실패했다.

```sql
PRAGMA ignore_check_constraints = ON;
UPDATE tasks SET status = 'invalid-state' WHERE id = 'AIK-001';
```

SQLite는 이 PRAGMA로 CHECK 제약 검사를 끌 수 있다. 이번 환경에서는 같은 잘못된 파일에 대해 읽기 전용 `integrity_check`의 거짓 통과도 관측했으므로, 해당 검사만으로 enum·문자열·정수 범위의 유효성을 판단하지 않도록 했다. 이 환경 관측을 모든 SQLite 버전의 동작으로 일반화하지 않는다. [SQLite PRAGMA 공식 문서](https://www.sqlite.org/pragma.html#pragma_ignore_check_constraints)

복원은 필요한 PRAGMA와 정상 스키마 작성만 허용하고, 외부 DB 연결·확장 실행·가상 테이블/트리거 생성·제약 우회를 거절한다. 복원 후에는 제약을 다시 켜고 신뢰 스키마와 독립 값 검사를 수행한다. 상태 이력 검사는 관계적 일관성을 확인하는 기능이며, 같은 파일을 임의 수정할 수 있는 사람에 대한 암호학적 위변조 방지 기능은 아니다.

### 3. adapter 구현과 실제 지원을 구분해 출시 모순을 없앴다

수정 전 AIK-014/015는 실제 공식 로그인·실행 성공을 요구했고, 019·022·082 및 첫 출시 66개 전체의 선행 관계에 포함돼 있었다. 그래서 DEC12가 어떤 경로를 선택·미지원으로 두더라도 그 경로의 실제 성공이 출시 전제가 되는 모순이 있었다.

수정 후 012~015는 **구현 코드와 성공·실패 protocol fixture**를 완료 근거로 요구한다. 미지원만 반환하는 stub은 완료가 아니다. 실제 계정 인증은 022, runtime/역할의 model·effort 관측은 082, 실제 도구 실행과 GUI·출시는 044/059/064에서 검증한다. 모두 같은 지원 matrix revision/digest에 연결한다.

| 계획상의 상황 | 수정 후 기대 결과 | 확인 방법 |
| --- | --- | --- |
| 공통 계약 완료, 특정 adapter 구현은 blocked | AIK-019 공통 registry 개발 가능 | 메모리 DB의 선행 잔여 수 0·ready 확인 |
| adapter 코드·필수 qualification 완료, 선택 경로만 라이브 미지원 | 그 선택 상태 때문에 추가 출시 차단 없음 | 완료 기준 독립 검토·가상 계획 그래프 조회 |
| 필수 경로 실패로 AIK-059 qualification blocked | AIK-064 출시 차단 | 메모리 DB의 미완료 선행 1·ready 제외 확인 |

이 표의 가상 상태는 폐기 가능한 메모리 사본에서 관계를 조회한 것이다. 실제 제품 qualification이나 장부의 완료 상태를 변경한 결과가 아니다. 장부 도구는 provider 지원을 자동 판정하지 않는다. AIK-001에서 만드는 제품 matrix와 실제 완료 근거 검토가 그 역할을 맡는다.

두 벤더, API/지원 구독, 총괄/worker 도구 실행의 제안 범위는 유지했다. 필수 범위를 변경할 때는 결정·영향·재검증 근거가 필요하다. Windows GUI·멀티벤더 인증·사용자 지정 총괄이라는 사용자 확정 요구와 기존 confirmed 결정은 변경하지 않았다.

### 4. 원격 입력과 시크릿의 실제 보장 범위를 보강했다

원격 실행은 송신 측의 로컬 절대경로를 하위 worker에게 넘기는 것만으로 성립하지 않는다. 067/071은 논리 입력 identity·revision·상대경로·digest와 수신 측 경로 매핑을 정의하고, 허용 root에 입력을 준비한 뒤 bytes·freshness·권한을 검사하도록 보강했다. 074는 송신 측에만 있는 파일과 선행 산출물을 빈/다른 root의 수신 환경에서 읽는 실제 시험을 요구한다. 원래 VM Task의 권위는 유지한다. [최초 설계](initial-design.ko.md) · [VM 입력·실행 권위 설계 기준선](https://github.com/jaeseongs95/vibemarshal/blob/32bb0f9dd9f024045d24487312b50f5b703573a3/docs/orchestration-redesign.md)

Windows DPAPI의 일반적인 복호화 경계는 사용자 로그온 자격이고, CredRead는 현재 token의 로그온 세션에 연결된 자격 증명 집합을 읽는다. 따라서 앱 broker의 작업 범위 검사가 동일 사용자 native 프로세스의 OS API 접근까지 자동 격리한다는 가정은 하지 않는다. 004/009/018/035/061에 실제 principal·trust profile·권한 및 합성 비밀 시험을 넣었다. 강한 격리를 광고한 경로는 그 격리를 실제 검증하고, trusted same-user 경로의 통과를 같은 의미로 기록하지 않는다. [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) · [CredRead](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreada) · [VM A2 경계](https://github.com/jaeseongs95/vibemarshal/blob/32bb0f9dd9f024045d24487312b50f5b703573a3/README.md)

테스트는 Python 표준 라이브러리와 임시 장부만 사용한다. 동시성 시험에서는 실제 프로세스를 실행하고 파일 게시 직전 시점만 제어했다. 교체 실패는 `PermissionError`, 생성 실패는 주입된 `OSError`로 검사했다. native Windows에서 이 코드를 실행한 결과는 없으며, 이 고장 주입을 Windows qualification으로 세지 않았다. 실제 Python·SQLite·OS 버전과 테스트별 결과는 [validation.json](../planning/validation.json)에 기록한다.

## 아직 실제로 검증해야 하는 것

이번 도구·계획 수정에서 재현한 미해결 결함은 남기지 않았다. 다음은 제품 구현과 실제 환경이 있어야 수행할 기존 미완료 태스크다.

- **Windows native 동작:** vault/다른 사용자/잠금, GUI·IPC, 설치·업데이트·재시작·서명. 장부 도구의 Windows 잠금 분기도 실제 Windows 실행이 필요하다.
- **지원 matrix 확정과 라이브 검증:** provider·host·역할·모델/effort별 실제 인증과 도구 실행, 필수·선택 구분.
- **AGS/VM 선행 조건:** 호환 AGS plugin A2 conformance와 runtime 관측 receipt. 설치형 근거 없이 통과 처리하지 않는다.
- **원격 연합:** 서로 다른 실행 환경에서 입력 준비·위임·결과·단절/취소 회복.

구현 착수 순서는 AIK-001의 실제 통합 계약·지원 matrix, AIK-002의 Windows GUI/sidecar 검증, AIK-003의 Windows 지원·배포 형식 결정을 우선한다. 이 세 항목은 현재 선행 작업 없이 착수할 수 있다.
